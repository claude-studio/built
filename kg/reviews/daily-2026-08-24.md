## 목표와의 연결

- 명시적 `/built:apply`는 사람이 의도와 적용 결정을 유지하면서 control plane이 검증된 실행 결과를 root의 신뢰 가능한 상태로 연결하므로 GOAL-1의 핵심 성공 기준을 직접 전진시킨다.
- patch 또는 fast-forward 한 방식, preflight failure의 무변경 종료, machine-readable failure code는 자동화의 관측 가능성과 복구 가능성을 높인다.
- apply 성공 뒤 control-plane writer만 `state.json` evidence를 갱신해 provider가 파일 계약을 직접 소유하지 않는 비가역 원칙을 유지한다.
- dry-run과 실제 apply의 상호 배타성은 사용자의 점검 의도가 mutation으로 바뀌지 않게 하며, Reviewer FAIL과 회귀 테스트가 이 경계를 강화했다.
- issue·ADR·workflow·계약 문서와 runtime 구현을 같은 PR에 묶어 특정 feature의 현재 상태와 이유를 문서와 runtime에서 함께 추적할 수 있게 했다.
- Telegram 실패를 완료로 처리한 상태, 미실행 운영 이슈 누적과 빈 다음 제품 큐는 신뢰 가능한 완료 상태와 자동화 복구 가능성 기준에 여전히 맞지 않는다.
- `BUI-966`의 Multica 연결 PR 목록이 빈 상태는 issue-PR 추적성 SSOT가 GitHub·KG mapping과 일치해야 한다는 운영 기준의 드리프트다.
- `BUI-924`, `BUI-346`의 외부 차단이 지속되는 동안 독립 실행 가능한 다음 제품 작업이 없는 것은 GOAL-1 진전을 연속적으로 유지하지 못할 위험이다.

## 재발 방지 포인트

- daily review는 제품 구현 merge와 운영 기록 commit을 구분해 GOAL-1 직접 진전을 계산한다.
- ready backlog 공급을 성과로 계산할 때 실제 Builder→Reviewer→Recorder→Finisher lifecycle과 merge evidence까지 확인한다.
- dry-run entrypoint는 실제 mutation 명령과 상호 배타적으로 분기하며 한 invocation에 연속 배치하지 않는다.
- preflight failure는 root와 `state.json` 양쪽 무변경을 임시 Git 저장소 회귀 테스트로 고정한다.
- PR merge를 issue-PR 연결 테이블, KG mapping, 이슈 상태가 자동으로 모두 정합해졌다는 뜻으로 간주하지 않는다.
- 보고·알림 작업은 콘텐츠 생성, 필수 채널 전달, 상태 종료를 별도 evidence로 검증한다.
- 시점성 autopilot 실패는 무조건 사후 재실행하지 않고, 최신 canonical 기록과 누락 기간을 분리해 정리한다.
- 운영 `todo`를 ready product backlog로 집계하지 않으며 workspace 전체 상태와 built 프로젝트 큐를 구분한다.
- 외부 인증 blocker가 있어도 독립 실행 가능한 GOAL-1 직접 기여 작업을 최소 1건 유지한다.
- checker 결과는 기존 누적 finding과 이번 변경이 새로 만든 finding을 구분해 기록한다.
