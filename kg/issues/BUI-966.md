## 목표

완료된 execution worktree 결과를 사용자가 명시적으로 선택했을 때만 root working tree에 적용한다.
적용할 수 없는 상태에서는 root와 lifecycle SSOT인 `state.json`을 바꾸지 않고, machine-readable failure code와 복구 방향을 제공한다.

## 구현 내용

- `scripts/apply.js <feature>`와 `/built:apply <feature>` entrypoint를 추가했다.
- control root의 state와 registry pointer로 canonical worktree path, expected branch, resultDir을 해석하고, run 완료 여부와 root 적용 상태를 함께 preflight한다.
- commit 없는 worktree 변경은 untracked 파일을 포함한 `git diff --binary` patch와 `git apply --check`를 통과한 경우에만 적용한다.
- committed worktree branch는 uncommitted 변경이 없고 root HEAD에서 fast-forward 가능한 경우에만 `git merge --ff-only`로 적용한다.
- dirty root, committed/uncommitted mixed 상태, patch conflict, non-fast-forward, stale pointer, branch mismatch는 root와 state를 바꾸지 않고 거부한다.
- `--dry-run`은 preflight와 예정 방식만 출력한다. skill invocation도 dry-run과 실제 apply를 상호 배타적으로 분기한다.
- 성공한 뒤에만 control-plane writer가 `state.execution_worktree.root_applied`, `root_apply_status`, `root_apply_summary`, method, 적용 시각, commit 또는 patch hash evidence를 기록한다. provider는 파일 계약을 직접 쓰지 않는다.
- 이미 적용됐거나 적용할 변경이 없는 경우는 명확한 no-op으로 수렴한다.
- patch 적용 뒤 cleanup은 state에 기록된 patch hash와 현재 worktree 변경이 같을 때만 허용해 적용 이후 추가 변경을 보존한다.
- `status`, `cleanup`, `provider-doctor`, `docs/contracts/file-contracts.md`, `docs/ops/run-worktree-handoff.md`를 새 명령과 정렬했다.

## 결정 내용과 이유

- `/built:run`은 계속 root를 자동 변경하지 않는다. execution worktree 격리와 사용자 선택 경계를 유지하기 위해 apply는 별도 명시 호출로만 시작한다.
- patch와 fast-forward 중 한 방식만 선택한다. mixed 상태나 non-fast-forward 병합을 자동 처리하면 적용 범위와 충돌 해결 책임이 불명확해지기 때문이다.
- preflight 실패는 root/state 무변경으로 끝내고, 성공 뒤에만 state evidence를 남긴다. lifecycle 판단과 실제 Git 결과의 의미를 분리하지 않기 위해서다.
- dry-run과 실제 apply를 같은 skill invocation에서 연속 실행하지 않는다. 사용자가 점검만 요청한 호출이 mutation으로 이어지는 회귀를 막기 위해서다.
- patch hash는 원본 patch를 state에 저장하지 않고도 cleanup 시 적용 이후 추가 변경을 구분할 수 있는 최소 evidence로 선택했다.

## 알려진 실패 모드와 비범위

- Git 적용 성공 직후 `state.json` 원자 쓰기가 실패하는 극단적 I/O 오류는 `state_update_failed`로 보고한다. root 적용을 자동 rollback하지 않으며, root의 실제 Git 상태를 확인한 뒤 state를 복구해야 한다.
- dirty root 위 강제 적용, 충돌 자동 해결, partial apply, non-fast-forward 자동 병합, 범용 rollback 엔진은 비범위다.

## 재발 방지 포인트

- `/built:apply --dry-run`과 실제 apply는 같은 skill invocation에서 상호 배타적이어야 한다.
- apply 방식은 binary patch 또는 fast-forward 하나로만 수렴해야 하며, mixed 상태와 non-fast-forward를 자동 병합으로 우회하지 않는다.
- preflight failure code를 추가하거나 바꿀 때 root와 `state.json`이 모두 무변경인지 임시 Git 저장소 회귀 테스트로 고정한다.
- state evidence는 Git 적용 성공 뒤 control-plane writer로만 기록한다. provider에 root 또는 `state.json` 쓰기 책임을 넘기지 않는다.
- patch 적용 뒤 worktree가 다시 바뀌면 patch hash 불일치로 cleanup을 중단해 후속 변경을 보존한다.
- `state_update_failed`는 preflight failure와 다르다. Git 적용이 이미 끝났을 수 있으므로 자동 재시도 전에 root 실제 상태를 먼저 확인한다.
